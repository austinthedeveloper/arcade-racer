## Where the game stands (2026-10-31, after v0.1.0)

**Built.** Pseudo-3D renderer with curves, hills, jumps, hill pitch, fog, road-spanning sprites,
tunnels and Neon's tunnel walls. Eight stages drivable back to back, each with its own clock.
Twelve cars with stat-based tuning. Same-direction traffic with stage specials. Seven seeded AI
rivals with personalities, rubber banding and difficulty; positions, drafting, the launch boost,
scoring bonuses and points. Grand Tour, Single Race, Time Attack with a ghost and Free Drive from
a mode select; save data, unlocks, a results screen with standings, a pause menu, the finish
spectacle and an attract-mode demo. An FX layer (smoke, kick-up, sparks, nitro, speed lines,
fireworks). Options on pages: display, shake and flash sliders, MPH or KPH, steering and braking
assists, remapping, resets. Wheel calibration, saved profiles, the F1 input overlay. Placeholder
audio with a gear-and-rev engine model. Windows, macOS, Linux and Web exports with an auto-updater,
CI with golden traces for every stage and screenshot regression, a tag-driven release workflow.

**Not built.** Steering lock in Options (WH-1), force feedback, weather, multi-layer parallax,
power slides, manual gears, oncoming traffic, production car sprites and paint colors, the music
radio, the announcer and callouts, HUD v2, the map stage select, colorblind HUD and subtitles.

## The six months at a glance

Capacity assumption: one developer part time, plus Claude. About four medium items a month,
or one large item and two small ones. Each month ends with a tagged pre-release so there is
always a build to play.

| Month | Theme | Headline features | Release |
|---|---|---|---|

## Tracking on GitHub

The feature list is mirrored on GitHub (populated 2026-10-31), and the docs stay the source of the
wording while GitHub tracks state:

- **Issues.** One per feature, titled with its ID (`RC-8 Power slide`), labelled with its group
  (`RC: racing core` and so on), its size (`size: S`, `M`, `L`) and `roadmap`. Dependencies in the
  body read `WS-1 (#28)`, so GitHub cross-links them.
- **Milestones.** M1 (November 2026) to M6 (April 2027), one per month of the table above, each
  with its theme and due date. The milestones page is the month-by-month roadmap.
- **Project.** [arcade racer roadmap](https://github.com/users/austinthedeveloper/projects/4) holds
  every issue with Month, Group, Size, Start date and Target date fields, and a Status of Backlog,
  Todo, In progress or Done. Month 1 starts in Todo, the rest in Backlog.

When a feature is finished, close its issue and run `python3 tools/roadmap_sync.py --fix-board --write-docs`:
it moves the project item to Done, ticks the row and rewrites the status table above. A PR
stacked on another branch doesn't close its issues when it merges, so check the report after a
stack lands. When a group doc changes a
feature, update its issue to match. A new feature takes the next ID in its group doc and gets an
issue in the same shape.

**Landing a stack of PRs.** A month's work often goes up as branches stacked on each other
(each PR's base is the branch below it). The repository deletes a head branch once its PR merges,
and GitHub closes, not retargets, a PR whose base branch is deleted. So merge from the bottom,
and point the next PR's base at `main` before merging the one under it:

1. `gh pr edit <child> --base main`, then `gh pr merge <parent> --merge`, for each pair, bottom up.
2. Merge the top one, then check that `main` matches the top branch (`git diff origin/main <top>`).
3. Issues close when their `Closes #N` reaches `main`. Run `roadmap_sync.py --fix-board --write-docs`,
   commit the ticks on their own branch, and close a milestone with no open issues left.

A fix found in CI for a branch low in the stack goes on that branch, and is then merged up
through the branches above it, so every PR stays green on its own.

**Adding a batch of stories** (the second year, 2026-11-10):

1. Write the rows in the group docs first (next IDs, Size, Month, Needs, Done when), and add the
   months to `MONTHS` in `tools/roadmap_sync.py`.
2. Create the new milestones (`gh api repos/austinthedeveloper/arcade-racer/milestones -f title="M7 May 2027: ..." -f due_on=...`),
   titled `M<n> <Mon YYYY>: <theme>`, as `roadmap_sync` finds a month's milestone by its `M<n>`.
3. Add the new months to the project's Month field, and any new group to its Group field. Use the
   GraphQL `updateProjectV2Field` with every existing option passed back with its `id`. An
   option sent without its id is a new option, so every item that had the old one loses its
   value. The `gh` CLI can't add an option, so send the mutation with `gh api graphql`.
4. `python3 tools/roadmap_sync.py --create-issues` opens an issue per row with no issue, with
   labels, milestone and project fields. Ninety issues in one go trips GitHub's secondary rate
   limit on the project calls; wait a few minutes and run it again, as it skips rows that
   already have an issue.
5. Give each new item its Start date and Target date: the first and last day of its Month.
6. `python3 tools/roadmap_sync.py` reports 0 problems, and the overview's tables cover the new
   months.

## Reading the group docs

Each group doc has the same shape: what is built today, a feature table, open decisions and test
notes. Feature IDs are the group code plus a number (RC-1). Columns:

- **Size.** S is a day or two. M is about a week. L is two weeks or more.
- **Month.** 1 to 6 as in the first table, 4 to 15 for the second year (month 15 is Jan 2028). "Stretch" means after April 2027 unless a month runs light.
- **Needs.** Other feature IDs or docs this depends on.
- **Done when.** The check that closes the item, including the test it adds.
